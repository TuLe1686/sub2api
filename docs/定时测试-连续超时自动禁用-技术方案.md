# 定时测试：连续超时自动停用与自动恢复技术方案

> 目标基线：Sub2API `v0.1.177`@`073e92d17178a1ccdb0a27017f572f10c9c7ab62`
>
> 更新日期：2026-08-16
>
> 实现形态：在既有 TTFT 补丁之后应用的第二个源码补丁。本文记录实际实现，不再使用早期 `timeout_ms/timeout_state/disabled` 草案。
>
> V1 修订（2026-08-16）：三路独立复核后，补全所有权表独立性、scanner 优先级与 aging、过期 claim 周期性 heal、四原因分类、管理员 `plan_version` fencing、guard 与 `auto_recover` 分离、配置时区注入、灰度上线顺序与回滚处理。状态值已用实际代码定论：管理 API 接收 `inactive`，service 原样落库，响应原样返回，前端类型也是 `inactive`；新功能统一使用 `inactive`，不沿用遗留的 `StatusDisabled="disabled"` 常量。

## 一、目标与兼容性

功能扩展现有定时测试，不新增外部守护程序：

1. 对单次尝试设置截止时间；
2. 超时后按计划内延迟快速重试，默认 10 秒和 20 秒；
3. 只有整次逻辑执行的所有尝试均超时，才增加连续超时计数；
4. 成功或非超时失败都清零连续链；
5. 达到阈值后支持影子记录或自动把账户置为 `inactive`；
6. 只允许所有者计划通过成功恢复探测重新启用账户；
7. 提供 kill switch、强制影子、平台熔断和停用预算。

存量计划默认 `timeout_protection_mode = 'off'`。关闭模式仍只执行一次测试，不启用 per-attempt timeout、快速重试或保护计数。

### 1.1 inactive 语义

guard 只做 `active ↔ inactive` 状态迁移，不修改 `schedulable`，不接管 `error` 或人工 `inactive` 的账号。代码常量 `ScheduledTestAccountStatusInactive = "inactive"`，不使用遗留的 `StatusDisabled = "disabled"`。恢复 CAS 要求账户仍为 `status=inactive, schedulable=false, error_message="scheduled test consecutive timeouts"`，不满足则记录 `blocked/manual_override`，不覆盖人工决定。

## 四、领取、续租与 fencing

### 4.1 ClaimDue

runner 每 10 秒扫描一次，通过 `FOR UPDATE SKIP LOCKED` 批量领取：

- 新逻辑执行生成 UUID `execution_id`；
- 租约过期接管保留原 `execution_id`；
- 每次领取生成新 UUID `claim_token`；
- 记录当前 `plan_version` 为 `claim_plan_version`；
- 使用数据库 `NOW()` 计算租约到期时间。

计划更新时 `plan_version + 1` 并清理 claim，使旧 worker 立即失去 finalize 权限。

**扫描优先级与 aging**：`ClaimDue` 按 `recovery > timeout_retry > scheduled` 优先级排序，并对逾期普通任务做 aging（逾期越久优先级越高），避免低频 recovery 计划被大量 scheduled 任务饿死。具体实现：`ORDER BY` 使用优先级权重 + `next_run_at` 组合，`LIMIT` 取空闲 worker 容量。优先级判定：

- `recovery`：计划持有 `scheduled_test_account_ownership`（账号被 guard 禁用，等待恢复探测）；
- `timeout_retry`：`consecutive_timeout_count > 0` 且未达阈值（处于连续超时链中）；
- `scheduled`：普通定时任务。

### 4.2 续租

`RenewClaim` 同时校验：

- plan ID；
- claim token；
- claim version 与当前 plan version；
- 租约尚未过期。

成功时返回数据库生成的新到期时间。runner 根据实际到期时间设置安全边界；数据库错误会快速重试，无法在安全边界前确认则取消执行。续租持续到 finalize 返回。

### 4.3 FinalizeClaim

finalize 事务先按 token/version 锁定计划行，随后读取 `clock_timestamp()`。只有 `claim_expires_at > lockedAt` 才继续。这样不会因为 PostgreSQL `NOW()` 固定为事务开始时间，而接受一个在等待行锁期间已经过期的 claim。

最终计划更新再次校验 token/version；影响行数必须等于 1，否则整个事务回滚并返回 `ErrScheduledTestClaimLost`。

`FinalizeClaim` 是唯一的完成写入入口——单 PostgreSQL 事务内完成结果幂等插入/裁剪、计划状态与 `next_run_at` 更新、owner 增删、账号 `active↔inactive` 条件更新、scheduler outbox 写入。事务提交后再刷新 scheduler snapshot。不保留可被任意组合调用的 `UpdateGuardState` / `SetDisabled` / `Reenable` 等方法，否则调用方仍能拆散事务。

### 4.4 HealExpiredClaims

runner 定期（每扫描周期或独立 ticker）分批调用 `HealExpiredClaims(cutoff, limit)`，不只在启动时修复。过期 claim 的处理规则：

- 只重排同一 `run_mode`：`recovery` 计划重排为 recovery，普通计划重排为 scheduled；
- **不推进 timeout 计数**：过期 claim 视为执行中断，`consecutive_timeout_count` 不变；
- 清理 `claim_token` / `claim_plan_version` / `claim_expires_at`，保留 `execution_id` 供接管 worker 复用；
- `next_run_at` 重排为 `NOW()`，使下一个扫描周期立即被领取。

这避免旧 worker 在 claim 回收后覆盖新结果（`next_run_at=NULL` 不是可靠租约）。

## 五、尝试状态机

### 5.1 超时识别

仅以下错误属于 timeout：

```go
errors.Is(err, context.DeadlineExceeded)
errors.As(err, &netErr) && netErr.Timeout()
```

错误消息包含 `timeout` 但类型不是 timeout 时，分类为普通失败。

`RunTestBackground` 必须返回原始 `testErr`，不能只返回结果文本，否则类型信息会丢失。`RunTestBackground` 保持同步执行，不把 Gin handler 丢进 goroutine（唯一调用方已核实）。

### 5.2 重试

有效模式为 `shadow/enforce` 时：

```text
attempt 1 --timeout--> wait retry_delays[0]
attempt 2 --timeout--> wait retry_delays[1]
attempt 3 ...
```

- 每次尝试独立 `context.WithTimeout`；
- success 或 failure 立即结束；
- 仅 timeout 继续；
- 父 context 取消时不生成业务结果；
- 总 execution budget = 所有尝试 timeout 总和 + 所有等待总和。

如果总预算在等待下一次重试时耗尽，返回当前 timeout 结果以完成 fenced finalize，避免 claim 周期性过期接管却永不落结果。

### 5.3 四原因分类

复核要求分离四种执行失败原因，只有「账号测试阈值」进入连续 timeout 链：

| 原因 | 判定 | 是否计入 timeout 链 | protection_action |
|---|---|---|---|
| 账号测试超时 | `DeadlineExceeded` / `net.Error.Timeout()`，且有效模式非 off | 是 | `would_inactivate` / `inactivated` |
| runner shutdown | 父 `context.Canceled` | 否 | 不生成业务结果，claim 由 heal 回收 |
| 网关/基础设施失败 | 非 timeout 的网络错误、DNS、连接拒绝、5xx 网关错误 | 否 | `none`，`classification=failure`，清零计数 |
| 业务 failed | 上游返回业务错误（4xx、模型不可用等） | 否 | `none`，`classification=failure`，清零计数 |

`classifyScheduledTestAttempt` 当前分 `success/timeout/failure` 三类；网关/基础设施失败与业务 failed 都归入 `failure` 并清零计数，不进入连续 timeout 链。runner shutdown 通过 `context.Canceled` 提前返回，不写结果。breaker 打开时 `scheduledTestDisableAllowed` 返回 `platform_circuit_open`，不计 timeout。

## 六、有效模式

保存模式与运行模式分开：

```go
func effectiveScheduledTestTimeoutProtection(mode string, cfg *config.Config) (string, string)
```

规则：

| 保存模式 | 全局配置 | 有效模式 | 覆盖原因 |
|---|---|---|---|
| `off` | 任意 | `off` | 空 |
| `shadow/enforce` | `enabled=false` | `off` | `kill_switch` |
| `enforce` | `enabled=true, force_shadow=true` | `shadow` | `force_shadow` |
| 其他 | 已启用 | 保存模式 | 空 |

runner 在 finalize 前重新计算有效模式，因此执行期间打开 kill switch 也会阻止计数和停用。

## 七、账户所有权与事务

### 7.1 自动停用

达到阈值后，`shadow` 只记录 `would_inactivate`。`enforce` 在同一事务中：

1. 锁定账户；
2. 锁定/检查所有权；
3. 获取平台级 advisory transaction lock；
4. 检查平台熔断和窗口预算；
5. 插入账户所有权，保存原 `schedulable/error_message`；
6. CAS 将仍为 `active` 的账户改成 guard 固定状态（`status=inactive, schedulable=false, error_message="scheduled test consecutive timeouts"`）；
7. 写 scheduler outbox；
8. 写结果、计数、下次时间并清理 claim。

账户 CAS 为零行时返回 `ErrScheduledTestAccountMutationConflict`，事务回滚，包括刚插入的所有权。

### 7.2 恢复

拥有所有权的计划仍按 cron 领取，结果运行模式标记为 `recovery`。成功时，恢复 CAS 要求账户仍为：

```text
status=inactive
schedulable=false
error_message="scheduled test consecutive timeouts"
```

满足时还原原状态并删除所有权；不满足说明管理员已接管，记录 `blocked/manual_override`，不覆盖人工决定。

**guard 自动恢复与 `auto_recover` 分开**：guard 恢复先在 `FinalizeClaim` 事务内释放所有权/恢复账号状态（CAS active）；事务提交成功后，只有 `auto_recover=true` 时才调用现有 error/rate-limit 运行态清理（`tryRecoverAccount`）。`canRunScheduledTestAutoRecover` 检查 `TimeoutProtectionMode == off` 且无所有权时才允许普通 auto-recover，避免与 guard 恢复冲突。只有当账号没有其他 owner 时才恢复 active。

### 7.3 计划更新与删除

持有所有权的计划默认禁止被停用或删除，返回 409。只有调用方显式传 `restore_owned_account=true` 时，才先在事务中恢复并释放所有权。恢复 CAS 失败则整个计划变更回滚。

update DTO 三个配置字段全部使用指针：`nil=不改`，数值 `0=关闭`；重试数组显式空值返回 400。owner 存在时删除计划、禁用计划或把 guard 配置改为 `0`，默认返回 409；前端弹出明确选择：恢复账号并释放 owner，或保持 `inactive` 并移交人工。

普通 `auto_recover` 先检查账户是否存在任何 timeout guard 所有权，有则跳过。

### 7.4 管理员接管 fencing

管理员显式修改账号 `status` 时，管理员优先：触发器 `release_scheduled_test_ownership_on_manual_status` 事务性撤销 guard ownership。为确保旧 claim 无法再禁用/恢复，管理员路径还需递增受影响计划的 `plan_version`，使正在运行的 worker 的 `claim_plan_version` 与新 `plan_version` 不匹配，fencing 失败（`FinalizeClaim` 返回 `ErrScheduledTestClaimLost`）。

触发器通过 session-local `sub2api.scheduled_test_owner_mutation=1` 区分 guard 自身事务与管理员手动操作，避免 guard 事务误触发自身。

## 八、全局安全阀

配置：

```go
type ScheduledTestTimeoutGuardConfig struct {
    Enabled                bool
    ForceShadow            bool
    ClaimLeaseSeconds      int
    MaxWorkers             int
    CircuitWindowSeconds   int
    CircuitMinSamples      int
    CircuitTimeoutRatio    float64
    DisableBudgetPerWindow int
}
```

默认：关闭、强制影子、租约 300 秒、10 workers、窗口 300 秒、最少 20 样本、比例 0.8、预算 3。

`circuit_timeout_ratio: 0` 是合法显式值，运行时不得偷偷替换回默认值。

平台熔断计算包含当前 timeout 候选。预算只数历史 `protection_action='inactivated'`，恢复不会返还同一窗口已经消耗的预算。

**灰度默认值**：首轮灰度部署时 `disable_budget_per_window` 调为 `1`（代码默认 3，部署时通过配置覆盖），观察一个完整 cron 周期后再逐步放大。

## 九、observe-only 测试

Scheduled runner 通过 `AccountTestOptions{ObserveOnly: true}` 调用连接测试。repository 和 token provider 检查该 context 标志，跳过所有测试副作用，包括：

- 凭据与 token 持久化；
- error/rate limit/model rate limit/overload/temp unschedulable；
- account extra；
- Agent Identity 自动恢复。

这使探测与保护状态变更分离，只有 fenced finalize 事务能停用或恢复账户。

## 十二、补丁与升级

提交历史固定为：

```text
v0.1.177 upstream
TTFT commit
Scheduled Test timeout guard commit
```

builder 从两个精确提交区间导出补丁，依次应用并独立校验文件白名单。任一补丁冲突、SHA 不匹配、范围越界或测试失败，构建必须 fail-closed。

应用使用私有 GHCR digest 和只读根文件系统。禁止容器内在线升级；后续升级流程为更新 upstream tag/commit、重审两个补丁、重新构建 baseline/patched、验证 digest 后再独立审批部署。

## 十三、配置时区

统一向 scheduled service 注入配置时区：cron 表达式在配置时区计算，`TIMESTAMPTZ` 以 UTC 存储。`computeNextRun` 当前使用 `time.Now()`（服务器本地时区），V1 改为注入 `cfg` 中的时区 `time.Now().In(loc)`，确保跨时区部署的 cron 触发一致。

- 配置项：`scheduled_test.timezone`（默认 `UTC`）；
- `computeNextRun(cronExpr, from)` 的 `from` 使用配置时区；
- `next_run_at` 列为 `TIMESTAMPTZ`，存储 UTC；
- handler 返回的时间由 API 层按客户端时区格式化，不影响存储。

## 十四、灰度与回滚

### 14.1 上线顺序

1. 迁移并部署新镜像，guard 默认关闭（`enabled=false`）；
2. shadow mode 观察一个完整 cron 周期，确认 `would_inactivate` 记录符合预期；
3. 少量账号开启 `enforce`，`disable_budget_per_window=1`；
4. 演练恢复（手动触发 recovery 探测）、熔断（模拟平台 timeout 比例飙升）、回滚；
5. 逐步扩大账号范围和预算。

实施、构建 validated manifest 后先停在部署门口，部署 B（us-biz）前单独确认。

### 14.2 回滚处理

回滚前必须先释放活动 claim 并重排 `next_run_at`，避免旧镜像（不含 guard 逻辑）留下永久 `NULL` 计划：

```sql
-- 回滚前执行
UPDATE scheduled_test_plans
SET next_run_at = COALESCE(next_run_at, NOW()),
    claim_token = NULL, claim_plan_version = NULL, claim_expires_at = NULL,
    execution_id = NULL
WHERE claim_token IS NOT NULL OR next_run_at IS NULL;
```

- 回滚到旧镜像后，guard 相关字段被旧代码忽略（不读取），但 `next_run_at` 必须非 NULL，否则旧调度器永不领取；
- `scheduled_test_account_ownership` 表保留，旧代码不读取，不影响运行；
- 已被 guard 置为 `inactive` 的账号需人工恢复，或保留 `inactive` 等待人工确认。

### 14.3 V2 留项

动态 worker 数、heartbeat 续租（当前为固定间隔续租）、同账号复杂仲裁、DLQ/replay 管理台和自适应 breaker 参数留到 V2。
