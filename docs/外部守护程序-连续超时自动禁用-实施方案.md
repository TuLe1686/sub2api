# 连续超时自动停用：实施方案

> 更新日期：2026-08-15

## 二、运行语义

### 2.1 计划配置

每个定时测试计划新增：

| 字段 | 含义 |
|---|---|
| `timeout_protection_mode` | `off`、`shadow` 或 `enforce` |
| `timeout_seconds` | 单次尝试的截止时间 |
| `consecutive_timeout_threshold` | 逻辑执行连续超时多少次后触发保护 |
| `retry_delays_seconds` | 同一次逻辑执行内的快速重试等待序列，默认 `[10, 20]` |
| `consecutive_timeout_count` | 已连续发生整轮超时的逻辑执行次数 |
| `plan_version` | 配置版本，更新计划时递增并使旧 claim 失效 |

旧计划默认 `off`。有效模式为 `off` 时保持原行为：单次调用、不应用本功能的尝试截止时间、不快速重试、不累计保护计数。

### 2.2 一次逻辑执行

`shadow` 或 `enforce` 模式下，一次逻辑执行由初始尝试和配置的快速重试组成。每次尝试使用独立 context：

1. 成功：立即结束，连续超时计数清零；
2. 非超时失败：立即结束，连续超时计数清零；
3. 明确的 deadline 或 `net.Error.Timeout()`：按重试延迟继续；
4. 所有尝试均超时：该计划的连续超时计数加一。

错误文本中出现 `timeout` 不构成超时。父 context 取消属于执行生命周期终止，不写成业务结果。

### 2.3 影子、生效与全局覆盖

- `shadow`：完整执行超时、重试和计数逻辑；达到阈值只写 `would_inactivate`。
- `enforce`：达到阈值且所有安全条件通过时自动把账户从 `active` 改为 `inactive`。
- 全局 kill switch 关闭时，保存的 `shadow/enforce` 有效模式统一变为 `off`。
- `force_shadow` 打开时，保存的 `enforce` 有效模式变为 `shadow`。

API 同时返回保存模式、有效模式和覆盖原因，前端展示真实运行状态。

## 三、claim、租约与幂等

计划领取使用 `FOR UPDATE SKIP LOCKED`。每次新领取生成：

- 稳定的逻辑 `execution_id`；
- 每次领取轮换的 `claim_token`；
- 领取时的 `claim_plan_version`；
- 数据库时间计算的 `claim_expires_at`。

租约过期后，新 worker 可接管同一个 `execution_id`，但会获得新 token。旧 worker 通过 token、版本和租约 fencing 失去写入权。

runner 在执行和 finalize 期间持续续租。续租无法在安全边界前确认时，取消正在进行的上游调用。finalize 先锁计划行，再读取 `clock_timestamp()` 验证租约，避免 PostgreSQL 事务起始时间导致等待锁期间过期的 claim 被误接受。

结果以 `(plan_id, execution_id)` 唯一。结果、计数、下一次运行时间、claim 清理、账户状态、所有权和 scheduler outbox 在一个事务内完成。

## 四、账户所有权与恢复

自动停用使用独立所有权表，记录：

- 哪个计划持有账户；
- 停用前的 `schedulable`；
- 停用前的 `error_message`。

自动停用只允许把仍为 `active` 的账户写成：

- `status = 'inactive'`；
- `schedulable = false`；
- `error_message = 'scheduled test consecutive timeouts'`。

拥有所有权的 inactive 账户继续按原 cron 进行 observe-only 恢复探测。只有所有者计划探测成功，并且账户仍保持以上完整 guard 写入状态时，才恢复为 `active` 并还原原 `schedulable/error_message`。

管理员修改 `status`、`schedulable` 或 `error_message` 会释放所有权。普通 `auto_recover` 在任何 timeout-guard 所有权存在时跳过，避免与所有者恢复竞争。

停用或删除仍持有所有权的计划默认返回 HTTP 409。管理端必须显式确认“恢复账户并释放所有权”，事务成功后才允许继续。

## 五、安全阀

配置段 `scheduled_test_timeout_guard` 包含：

```yaml
scheduled_test_timeout_guard:
  enabled: false
  force_shadow: true
  claim_lease_seconds: 300
  max_workers: 10
  circuit_window_seconds: 300
  circuit_min_samples: 20
  circuit_timeout_ratio: 0.8
  disable_budget_per_window: 3
```

真正停用前，以平台为粒度获取事务 advisory lock，并检查：

- 窗口内样本数与超时比例，当前超时候选也计入；
- 窗口内历史 `protection_action = 'inactivated'` 数量；恢复不返还预算；
- 账户是否仍可由该计划建立所有权并原子停用。

触发平台熔断、预算耗尽、账户冲突或人工接管时只记录阻断原因，不修改账户。

## 六、observe-only 探测

定时测试使用 `AccountTestOptions{ObserveOnly: true}`。定时探测不允许通过测试副作用改写凭据、错误、限流、模型限流、过载、临时不可调度或账户 extra，也跳过 token provider 的自动持久化与 Agent Identity 自动恢复。

这保证账户停用/恢复只由 timeout guard 的事务路径负责。

## 七、数据库迁移

- `224_scheduled_test_timeout_guard.sql`：新增计划/结果字段、历史结果分类回填、所有权表和人工接管触发器。
- `225_scheduled_test_execution_unique_notx.sql`：使用 `CREATE UNIQUE INDEX CONCURRENTLY` 建立 `(plan_id, execution_id)` 唯一索引。
- migration runner 在重试 225 前会清理同名 invalid index。

迁移 224 包含 `ALTER TABLE`、回填和 `SET NOT NULL`，可能在大表上持有较强锁并产生 WAL。生产前必须在 PostgreSQL 15 的 staging 或维护窗口测量表规模、执行时间、锁等待和 WAL；未测量前不得直接部署。

## 八、前端交互

`ScheduledTestsPanel.vue` 已增加：

- 超时模式、单次超时、连续阈值、重试延迟；
- 保存模式与有效模式、覆盖原因；
- 连续计数和所有权状态；
- 普通/恢复探测、成功/超时/失败、保护动作和阻断原因；
- 弹窗打开期间 15 秒轮询与手动刷新；
- 停用/删除所有者计划时的显式确认和 409 兜底。

内部枚举均有中英文映射，未知值回退显示原始值。

## 九、构建与发布

私有 builder 的目标链为：

```text
v0.1.177@073e92d17
  -> responses-reasoning-ttft.patch
  -> scheduled-test-timeout-guard.patch
```

builder 必须独立校验两个补丁的 SHA-256、revision 和精确文件白名单。baseline 从未打补丁源码构建前端与后端；patched 从两个补丁全部应用后的源码构建前端与后端。不得把 baseline 前端复制到 patched 镜像。

外部部署包名继续使用 `ghcr.io/<owner>/sub2api-ttft` 以兼容既有部署，但 OCI variant、release manifest、SBOM 和内部目录使用 `patched` 表示组合补丁成品。
